# ADR 0003. PostgreSQL — источник истины, Redis — вспомогательное хранилище (fail-open)

**Статус:** принято; пересмотрено 2026-10-12: сервер Redis заменён на Valkey, кэш задач удалён
вместе с модулем `tasks`

## Контекст

Нужны транзакции, инварианты на уровне БД и защита от гонок. Нужны и быстрые дешёвые
операции: защита от повторных POST мобильного клиента, ограничение частоты
запросов (в том числе против перебора паролей). Отказ вспомогательного компонента не должен
ронять основной сценарий.

## Решение

- **PostgreSQL** хранит все данные, включая сессии (`refresh_tokens`).
- **Redis** выполняет две роли, и ни одна не хранит данных, которых нет в Postgres:
  1. хранилище `Idempotency-Key`: `SET NX EX 30` (pending) → результат на 24 ч (completed),
     удаление при ошибке. Жизненный цикл реализован в `IdempotentExecutor` слоя application
     и покрыт unit-тестами на фейке;
  2. rate limit, фиксированное окно: `INCR` + `EXPIRE NX` в одной транзакции MULTI.
- **Fail-open.** Каждый вызов Redis обёрнут в
  `REDIS_FAILURES = (RedisError, TimeoutError, ConnectionError, OSError)`. Ошибка логируется
  (`redis_unavailable`, `op`) и считается в `redis_errors_total{op}`, а запрос продолжается:
  идемпотентность пропускается, лимит не применяется.
- Таймаут операции 200 мс и один немедленный повтор: повтор лечит соединение из пула,
  сломанное рестартом Redis. Больше повторов умножали бы таймаут, когда Redis завис.
- `/health/ready` при недоступном Redis отвечает `degraded` (200), а не 503.
- **Сервер — Valkey** (`valkey/valkey:9.1.2-alpine3.24`), BSD-3-форк Redis под Linux
  Foundation. Redis с 7.4 сменил лицензию (сейчас AGPLv3/RSALv2/SSPL), а ветка 7.2 под BSD-3
  больше не развивается. Valkey совместим по протоколу: клиент `redis-py`, настройки
  (`REDIS__URL`), имя сервиса `redis` в compose и метрики не меняются. Используются только
  `GET/SET NX EX/INCR/EXPIRE NX/DEL/PING`.

## Альтернативы

- **Fail-closed** (без Redis отвечать 503). Строже против дублей и брутфорса, но падение
  вспомогательного компонента роняет весь сервис.
- **Сессии в Redis.** Быстрее, но при fail-open потеря Redis означала бы разлогин всех или
  пропуск проверки отзыва. Сессии — данные, их место в Postgres.
- **Идемпотентность в Postgres.** Переживает рестарт Redis, но добавляет запись в БД на
  каждый POST и конкуренцию за строки.
- **Sliding window / token bucket.** Точнее на стыке окон, но сложнее (Lua или sorted sets).

## Последствия

- Пока Redis недоступен, повтор POST может создать дубль, а лимиты, включая защиту логина,
  не действуют. Это видно по `redis_errors_total` и `ready=degraded`.
- Каждая операция Redis во время отказа стоит до 2 × 200 мс. Улучшение — circuit breaker.
- Кэша чтения нет: новый модуль, которому он нужен, добавляет порт кэша и адаптер в
  `infrastructure/redis` по тем же правилам fail-open.
