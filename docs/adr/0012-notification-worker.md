# ADR 0012. Воркер уведомлений: taskiq будит воркер, очередь — таблица `notifications`

**Статус:** принято (2026-10-17). Уточняет разделы 10.3–10.5
[db-design.md](../db-design.md#103-отправка): cron «раз в минуту» заменён интервалом 15 с.

## Контекст

Уведомления ставятся в outbox `notifications` в транзакции изменения
([ADR 0010](0010-moving-domain-aggregates.md), [ADR 0011](0011-projects-api.md)), но до этого
решения их никто не отправлял. Требования:

- ни одно уведомление не теряется, а потерявшее смысл не уходит: условие проверяется в момент
  отправки (db-design, 10.1);
- доставка — Web Push с VAPID (решение 12 в db-design), точность — минуты: напоминания
  ставятся за часы и дни;
- запуск без ручных настроек (ТЗ, п. 8): ключи не выпускаются руками;
- данных, без которых сервис не работает, в Redis нет
  ([ADR 0003](0003-postgres-and-redis-fail-open.md));
- следующие фоновые задачи продукта (письма, экспорт PDF этикеток) не должны требовать
  своего самодельного цикла;
- остановившаяся отправка видна раньше, чем пожалуются пользователи.

## Решение

- **taskiq 0.13.0 + taskiq-redis 1.2.4**, стандартный инструмент фоновых задач, который
  db-design и планировал. Брокер — `TimeoutListQueueBroker` (наследник `ListQueueBroker` из
  taskiq-redis) на `REDIS__URL`, список `taskiq:notifications` (`WORKER__QUEUE_NAME`).
  Штатный слушатель делает BRPOP без таймаута, а у redis-py 8 таймаут сокета 5 с: на пустой
  очереди он бросал непойманный `TimeoutError`, и дочерний процесс воркера перезапускался
  каждые ~5 с. Наследник ждёт BRPOP по 2 с, а ошибки Redis ловит по правилу fail-open
  (`REDIS_FAILURES` + `report_redis_failure("task_queue_pop", …)`) и повторяет через 1 с.
  Код taskiq — только в `app/worker/` и `infrastructure/tasks/`, taskiq_redis — только в
  `infrastructure/tasks/`.
- **Два сервиса compose из того же образа**, без портов, в проде `restart: unless-stopped`:
  - `scheduler` — `taskiq scheduler app.worker.entry:scheduler --no-configure-logging`.
    `TaskiqScheduler` с `LabelScheduleSource`: у задачи `deliver_due_notifications` метка
    `schedule=[{"interval": 15, "schedule_id": "deliver_due_notifications"}]`
    (`WORKER__INTERVAL_SECONDS`, 15 с). Работает ровно один экземпляр; второй дал бы только
    пустые запуски. Healthcheck образа (проба `:8000` api) отключён (`healthcheck: disable`):
    иначе контейнер считался бы unhealthy и `docker compose up --wait` на деплое падал.
    Упавший планировщик завершает контейнер (в проде он перезапускается), а остановку видно
    по heartbeat `worker` и проверке `notifications`;
  - `worker` — `taskiq worker app.worker.entry:broker --no-configure-logging --workers 1
    --wait-tasks-timeout 30`. Вторая точка сборки рядом с `app.main`: на `WORKER_STARTUP`
    создаётся тот же контейнер Dishka (use cases и адаптеры, без HTTP), на `WORKER_SHUTDOWN`
    закрывается. Планировщик контейнер не создаёт и в БД не ходит.
- **Сообщение в Redis — только сигнал «пора».** Задача вызывает `drain`: до
  `WORKER__BATCH_SIZE` (100) созревших уведомлений, остальные ждут следующего запуска. Что
  отправлять, решает таблица. Потерянное, вытесненное (прод-Redis — `allkeys-lru`, 256 МБ) или
  повторное сообщение стоит задержки или пустого запуска, но не потери и не дубля уведомления.
  Если воркеры стоят, планировщик продолжает ставить сигналы; после рестарта они разбираются
  дешёвыми пустыми запусками.
- **Таблица — очередь.** Use case `DeliverNextNotification` берёт одно уведомление
  (`claim_next_due`: самое раннее `scheduled_at <= now`, `SELECT … FOR UPDATE SKIP LOCKED`) и
  обрабатывает его в своей транзакции. Несколько воркеров работают параллельно и не отправляют
  одно уведомление дважды.
- **Обработка уведомления:**
  1. `compose_message` заново проверяет причину по текущим данным
     (`AbstractNotificationContextReader`): проект удалён, получатель удалён или вышел из
     проекта, задача выполнена, коробка уже не `PACKING` → `CANCELLED`;
  2. отправка на все активные подписки получателя; 404/410 или непригодные ключи → подписка
     деактивируется;
  3. доставлено хотя бы на одну → `SENT`; подписок нет или все отпали → `SKIPPED`; только
     ошибки → `Notification.record_failure`: повтор через 1, 2, 4, 8 минут, после пятой
     попытки `FAILED`. Повторы — правило домена, а не ретраи taskiq.
- **At-least-once.** Строка заблокирована на время отправки, коммит — после неё. Если воркер
  упадёт, когда push-сервис уже принял сообщение, но коммита ещё не было, уведомление уйдёт
  ещё раз. Потерять его так нельзя. При остановке taskiq ждёт текущую задачу до 30 с
  (`--wait-tasks-timeout`), а compose даёт контейнеру 35 с до SIGKILL (`stop_grace_period`);
  если не успели, прерванное уведомление откатывается в `PENDING`.
- **Тексты собираются при отправке** (`application/notifications/services.py`), на русском и
  без содержимого коробок: экран блокировки видят посторонние. Срок задачи показывается в
  часовом поясе проекта.
- **Библиотека — pywebpush 2.5.0** в асинхронном режиме (`WebPusher.send_async` поверх
  aiohttp): шифрование aes128gcm (RFC 8291), подпись VAPID через py-vapid 1.9.4 (RFC 8292).
  Адаптер `WebPushSender` лежит в `infrastructure/push`; aiohttp, pywebpush, py_vapid и
  cryptography за его пределами запрещены.
- **Ключ VAPID создаётся сам.** Если задан `PUSH__VAPID_PRIVATE_KEY` (PEM), используется он;
  иначе файл `PUSH__VAPID_KEY_FILE`, который создаётся при первом использовании (`O_EXCL`,
  права 0600). В compose файл лежит в именованном томе `vapid`, общем для api и worker: api
  отдаёт браузерам публичную половину, worker подписывает приватной.
- **Логи** — тот же structlog JSON: `--no-configure-logging` отключает настройку логов taskiq,
  `app.worker.entry` вызывает `setup_logging` при импорте.
- **Остановка видна.** В `/health/ready` api добавлена вспомогательная проверка
  `notifications` (`NotificationLagProbe`): `degraded`, если самое старое ожидающее
  уведомление просрочено больше чем на `WORKER__MAX_LAG_SECONDS` (300 с). Воркер обновляет
  heartbeat-файл при старте и после каждого успешного запуска задачи; контейнер `worker`
  становится unhealthy, если файл не обновлялся 60 с. Подробности — в
  [observability.md](../observability.md#воркер-уведомлений).

Первая реализация того же дня была циклом asyncio в одном процессе без taskiq; её заменили
ради расширяемости и стандартного инструмента (первая альтернатива ниже).

## Альтернативы

- **Цикл опроса на asyncio в одном процессе.** Проще всего: один сервис, Redis для доставки не
  нужен, отказ Redis на уведомления не влияет. Но каждой следующей фоновой задаче пришлось бы
  дописывать свои очереди, повторы и расписание, а масштабировать — только целыми копиями
  цикла. Отклонено ради стандартного инструмента и расширяемости.
- **taskiq с `RedisScheduleSource`: расписание на каждое уведомление.** Отправка точно ко
  времени, но расписание живёт в двух местах (Redis и `notifications`), и их расхождение при
  потере данных Redis пришлось бы чинить пересчётом. Для минутной точности избыточно.
- **`LISTEN/NOTIFY` Postgres.** Мгновенная реакция на новую строку, но большинство уведомлений
  отложены на часы и дни, а о наступлении `scheduled_at` NOTIFY не сообщает: опрос нужен
  всё равно. Вдобавок долгоживущее соединение вне пула и потерянные сигналы при переподключении.
- **Отправка прямо в запросе API.** Нет нового сервиса, но запрос клиента ждёт чужие
  push-сервисы (до 10 с на каждый), ошибка доставки смешивается с ответом на изменение, а
  отложенным напоминаниям всё равно нужен фоновый процесс.
- **Потоки и синхронный pywebpush** (`asyncio.to_thread`, как в исходном 10.3). Работает, но
  нужен пул потоков и синхронный `requests`; в pywebpush 2.x есть `send_async`.

## Последствия

- Два новых процесса (`worker` и `scheduler`) вместо одного. Планировщик — ровно один
  экземпляр; воркер масштабируется репликами, `SKIP LOCKED` делит очередь.
- Redis на пути доставки. Данных в нём по-прежнему нет (ADR 0003), но пока Redis недоступен,
  сигналы не доходят и уведомления **задерживаются**, а не теряются: они уйдут после
  возвращения Redis. Это видно: `redis: degraded` в `/health/ready` сразу, через 300 с —
  `notifications: degraded`, контейнер `worker` — unhealthy (heartbeat старше 60 с). API при
  этом работает: fail-open для rate limit и идемпотентности не меняется.
- Задержка доставки — до интервала (15 с) после `scheduled_at`, при заторе больше. Затор
  дольше 5 минут виден как `degraded` в `/health/ready`.
- Редкий дубль после падения воркера во время отправки допустим (at-least-once).
- Внутри одного воркера отправка последовательная: медленный push-сервис (таймаут
  `PUSH__TIMEOUT_SECONDS`, 10 с) задерживает остальных.
- Мы переопределяем `listen()` закреплённой версии taskiq-redis (1.2.4). При обновлении
  библиотеки поведение проверяет `tests/integration/worker/test_task_queue.py`.
- Новая фоновая задача — ещё один `@broker.task` в `app/worker` (или своя очередь) без нового
  цикла и сервиса.
- Том `vapid` берегут как `pg-data`: без ключа все подписки браузеров ломаются (push-сервисы
  отвечают 403). Ротация — новый ключ и повторная подписка клиентов.
- Воркеру нужен исходящий HTTPS к push-сервисам производителей браузеров (Google, Mozilla,
  Apple); факт отправки им виден (db-design, раздел 2).
- Метрик Prometheus у воркера нет: состояние видно по readiness api, healthcheck контейнера и
  логам.
