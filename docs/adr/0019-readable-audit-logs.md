# ADR 0019. Читаемые логи действий пользователей

**Статус:** принято (2026-10-18)

## Контекст

С [ADR 0017](0017-logs-in-sage.md) логи прода ищутся в Sage, но читать их неудобно. Событие
выглядит как `project_created` с `user_id=0191…` и `project_id=0192…`: чтобы понять, кто и
что сделал, нужно идти в БД. Жюри, команда и поддержка разбирают сценарий «пользователь
сделал X, а увидел Y» по ленте логов, и им нужен ответ без SQL: «user alice created project
"Переезд в Казань"».

Кроме того, часть действий не логировалась совсем: создание, правка и удаление вещей и
комнат, правка коробок, задач и проекта (кроме сдвига даты), смена имени пользователя,
напоминания о содержимом коробок. В access-логе был только HTTP-статус: 409 не говорил,
какое правило нарушено.

Ограничения: application использует только stdlib `logging` ([ADR 0001](0001-clean-architecture-and-ddd.md));
у Sage одно поле в одном `system` должно сохранять тип; квота группы ограничена; секреты
(пароли, токены, `endpoint` push-подписки) и то, что пользователь ввёл в форму входа,
в логи не попадают.

## Решение

- **`username` в контексте запроса.** `get_current_user` уже перечитывает пользователя из
  БД на каждый запрос и теперь кладёт в `structlog.contextvars` не только `user_id`, но и
  `username`. Все строки запроса, включая access-лог, говорят, кто их вызвал. `Login` и
  `RegisterUser` передают имя аккаунта в событие сами.
- **Правило про логины уточнено.** Логируется только имя существующего аккаунта: после
  аутентификации, регистрации или успешного входа. Введённое в форму при неудачном входе
  (`login_failed`) по-прежнему не пишется: там может оказаться пароль.
- **Поле `message` с предложением.** Процессор structlog `add_message` в конце общего
  конвейера собирает текст по шаблону события из `app/infrastructure/log_messages.py`:
  `user alice created project "Дача" with 2 rooms`. Кто действовал — `username`, иначе
  `user_id`, иначе `anonymous`. Шаблоны лежат в infrastructure, поэтому application
  по-прежнему пишет только `event` и плоские поля через stdlib. Отсутствующее поле
  превращается в `?`, ошибка шаблона не теряет событие. Vector уже копирует `event` в
  `message` только если `message` нет, поэтому конфиг не меняется.
- **Шаблон обязателен.** Unit-тест сканирует AST `src/app` и сравнивает имена событий
  (`logger.info("…")`) с ключами `EVENT_MESSAGES` в обе стороны. Событие без шаблона или
  шаблон без события роняет `make check`.
- **Имена сущностей в событиях.** `project_name`, `room_name`, `item_name`, `task_title`,
  номер коробки `number` добавлены к событиям, а не только id. Для PATCH-операций поле
  `fields` перечисляет присланные поля (хелпер `sent_fields`), значения не логируются.
  Адреса, описания задач, фото и ответы модели в логи не попадают.
- **Новые события** для всех изменяющих use cases, которые раньше молчали (`item_*`,
  `room_created`, `room_renamed`, `box_updated`, `contents_reminder_*`, `project_updated`,
  `task_updated`, `username_changed`). Повтор без изменений, как и раньше, не пишется.
- **`error_code` в access-логе.** `error_response` оставляет `code` в состоянии запроса,
  middleware добавляет его в `http_request`. Поле есть только у ответов с ошибкой: `null` в
  успешных строках дал бы Sage второй тип поля.
- **Чтение не логируется отдельными событиями.** GET-запросы видны в access-логе; отдельное
  событие на каждый просмотр удвоило бы объём при ограниченной квоте Sage.

## Альтернативы

- **Текст сообщения формирует use case** (`extra={"summary": f"…"}`). Use case не знает
  `username` без лишнего запроса в БД, а формулировки расползлись бы по 40 файлам без
  проверки. Центральные шаблоны проверяются одним тестом.
- **`username` в claims access-токена.** Не нужен запрос в БД, но после смены имени логи
  до истечения токена показывали бы старое. Пользователь и так перечитывается на каждый
  запрос, поэтому имя из БД бесплатно и всегда актуально.
- **Только id, имена — через дашборд с join к БД.** Требует доступа к прод-БД у того, кто
  читает логи, и не работает в самом Sage.

## Последствия

- В Sage работают запросы `username="alice"`, `project_id="…"`, `event="http_request"
  status=409` (с `error_code`). Алерты и поиск строятся по `event` и полям: текст `message`
  можно переформулировать, а имена событий и полей — стабильный контракт.
- `username` и имена проектов, вещей и задач — персональные данные в логах. После удаления
  аккаунта они остаются в Sage до истечения срока хранения группы и в `docker compose logs`
  до пересоздания контейнера (ограничение в [architecture.md](../architecture.md)).
- Новое событие требует строки в `EVENT_MESSAGES` и в таблице событий
  [observability.md](../observability.md); тест напомнит о первом.
- Объём логов вырос примерно на одно событие на каждый изменяющий запрос.
