# ADR 0017. Логи прода в Sage через Vector

**Статус:** принято (2026-10-18)

## Контекст

Логи всех сервисов пишутся в stdout JSON-строками со сквозным `request_id`, но смотреть их
можно только командой `docker compose logs` на VM. Доступ к VM есть не у всей команды
(через Teleport), логи пропадают при пересоздании контейнера, а запрос, прошедший через
nginx и api, приходится собирать `grep` по двум потокам. Для жюри и для разбора инцидентов
нужен поиск по логам из браузера и алерты по ним.

Платформа наблюдаемости Spirit — Sage. Для нашей группы (`hack-led-12`) логи принимает
Logs Collector: `POST https://sage.spirit.t-education.com/api/<группа>/multiline/`, тело —
JSON-объекты через `\n`, заголовок `Authorization: JWT <Spirit API ключ>`, допускается
`Content-Encoding: gzip`. Каждый лог обязан содержать `env`, `system`, `inst` и
`@timestamp`, иначе он попадает в индекс dead-letters. `level` принимает фиксированный
набор значений (`INFO`, `WARN`, `ERROR`…). Индекс строится по `env`, `group`, `system`.
Квота группы ограничена: при превышении коллектор отвечает `429` с `Retry-After`.

Требования: основной сценарий не зависит от Sage; nginx, воркер и certbot тоже попадают в
Sage; ключ не попадает в образ приложения; конфигурацию можно проверить в CI.

## Решение

- **Отдельный сервис `vector`** (`timberio/vector:0.58.0-alpine`) в
  `docker-compose.prod.yml`. Источник `docker_logs` читает через Docker API stdout и stderr
  контейнеров с меткой `sage.logs=true` (api, worker, scheduler, migrate, nginx, certbot,
  redis). Преобразование (VRL, [vector.toml](../../docker/vector/vector.toml)):
  - JSON-строка становится полями события, текст остаётся одной строкой в `message`;
  - для structlog в `message` копируется `event`, чтобы в списке результатов Sage был текст;
  - `system` — имя сервиса compose, `inst` — имя контейнера, `env` — `SAGE__ENV` (`prod`),
    `version` — тег образа (git sha для приложения), `stream` — stdout или stderr;
  - `@timestamp` — время, когда Docker получил строку (UTC), а не `timestamp` приложения:
    часы контейнера не могут увести событие в dead-letters;
  - `level` приводится к значениям Sage: `warning` → `WARN`, у access-лога nginx уровень
    выводится из `status` (5xx → `ERROR`, 4xx → `WARN`), у текстовых строк — из `[warn]`
    или `ERROR:`. Неизвестный уровень уходит в `level_raw`, а не в `level`.
- **Отправка — HTTP sink** батчами до 500 событий или раз в 2 с, gzip. Ответы `429` и 5xx
  повторяются с backoff, события ждут в буфере (до 10 000), затем Vector притормаживает
  чтение логов Docker. Контейнеры от этого не зависят: Docker продолжает писать свои
  json-файлы.
- **Ключ — CI-переменная `SAGE__API_KEY`**, deploy пишет её в `.env` на VM, в контейнер
  попадает только к `vector`. Без ключа deploy не запускает `vector` (и удаляет старый), а
  деплой не падает из-за него: сервис поднимается без `--wait`, ошибка — предупреждение.
  Vector подставляет переменные окружения в конфиг только с флагом
  `--dangerously-allow-env-var-interpolation`; окружение контейнера задаёт только наш
  compose, поэтому риск подмены конфига через окружение не возникает.
- **Логи Postgres в Sage не отправляются.** При нарушении уникальности Postgres пишет в
  `DETAIL` значение ключа (имя пользователя), а логины мы по правилам не логируем. Сбои БД
  видны по логам api и `/health/ready`.
- **CI проверяет конфиг** job `vector`: `vector validate` и `vector test` с unit-тестами
  преобразования ([tests.toml](../../docker/vector/tests.toml)) на примерах строк api, nginx,
  certbot и Postgres.

## Альтернативы

- **Отправка из приложения** (logging handler поверх structlog, который шлёт батчи по HTTP).
  Не видит логи nginx, certbot и падения процесса до настройки логирования, требует фонового
  потока с буфером и ретраями в каждом процессе (api, worker, scheduler) и добавляет
  внешнюю зависимость в код. Vector даёт то же без изменений кода.
- **Sage Agent.** Коллектор Sage, который тоже читает логи Docker, но в alpha-версии,
  ставится скриптом на хост и настраивается в интерфейсе Sage. Его конфигурация не лежит в
  репозитории и не проверяется в CI, а на VM нужен ручной шаг установки.
- **Sage Kafka напрямую.** Нужны сетевой доступ к брокеру и выданный `clientId`, а HTTP-API
  коллектора доступен из интернета с одним ключом.
- **Logging driver Docker (gelf, syslog).** Меняет драйвер логов, после чего
  `docker compose logs` перестаёт показывать логи: теряется локальная диагностика на VM.

## Последствия

- Поиск в Sage: `group="hack-led-12" system="api" env="prod"`; запрос целиком через nginx и
  api — `group="hack-led-12" request_id="<id>"`.
- `vector` монтирует `/var/run/docker.sock`. Флаг `:ro` защищает только файл сокета, а не
  API: контейнер с сокетом фактически имеет права root на хосте. Порты `vector` не
  публикует, образ официальный и закреплён по версии.
- При перезапуске `vector` (каждый деплой) Vector читает логи уже запущенных контейнеров с
  момента своего старта: строки за несколько секунд простоя в Sage не попадут, на VM они
  остаются в `docker compose logs`.
- Поле с одним именем, но разными типами в одном `system` (например, `status` числом и
  строкой) Sage отклоняет, и событие уходит в dead-letters. Новые поля в логах называйте
  так, чтобы тип не менялся; проверка — `group="hack-led-12" system="dead-letters"`.
- Новый сервис в проде попадает в Sage, если добавить ему метку `sage.logs: "true"`
  (якорь `*sage-logs`). Фронтенд на той же VM может сделать то же в своём compose.
