# ADR 0008. Мягкое удаление: частичные уникальные индексы и изоляция конфликтов через SAVEPOINT

**Статус:** принято

## Контекст

Удалённого пользователя можно восстановить, и его данные нужны для аудита. При этом его
username должен сразу освобождаться для новой регистрации. Нарушение уникальности
при конкурентной регистрации должно превращаться в понятный 409, а не в 500 и не в
сломанную транзакцию SQLAlchemy.

## Решение

- `User.is_active = False` — мягкое удаление. Строка остаётся, все поиски по умолчанию её
  не видят (`get_by_id(..., include_deleted=True)` — явное исключение).
- Уникальность действует только среди активных:
  ```sql
  CREATE UNIQUE INDEX uq_users_username_active ON users (username) WHERE is_active;
  ```
  Несколько удалённых пользователей могут иметь одинаковый username. `RestoreUser` получит 409,
  если значение заняли, пока пользователь был удалён.
- Репозиторий выполняет `flush()` сразу, внутри `session.begin_nested()` (SAVEPOINT). При
  `IntegrityError` имя нарушенного индекса (`constraint_name` из asyncpg) превращается в
  `UsernameAlreadyTakenError`. Откатывается только savepoint:
  остальная транзакция запроса цела, сессия остаётся рабочей.
- Предварительная проверка `get_by_username` в `RegisterUser` нужна только для быстрого отказа
  до дорогого хэширования. Корректность при гонке обеспечивает индекс. Это проверяет тест с
  двумя конкурентными транзакциями.
- `update()` проверяет существование перед `merge()`, иначе merge молча вставил бы
  отсутствующего пользователя.

## Альтернативы

- **Колонка `deleted_at` и уникальность по `(username, deleted_at)`.** NULL не равен NULL, так
  что работает, но условие `WHERE deleted_at IS NULL` по смыслу то же, а булево поле проще.
- **Перенос удалённых в архивную таблицу.** Чистые индексы, но восстановление и внешние
  ключи сложнее.
- **Ловить `IntegrityError` при commit.** Ошибка теряет контекст (какое значение занято), а
  сессия после неё непригодна без rollback всей транзакции.

## Последствия

- Предикаты частичных индексов не видны `alembic check`, поэтому их сверяет отдельный тест.
- Запросы обязаны фильтровать `is_active`. Это инкапсулировано в репозитории, и use cases
  об этом не думают.
