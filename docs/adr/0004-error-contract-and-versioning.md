# ADR 0004. Единый контракт ошибок и версионирование API

**Статус:** принято

## Контекст

Клиентам нужен один способ разбирать ошибки, откуда бы они ни пришли: из правила домена,
из use case, из валидации FastAPI, от непредвиденного исключения или от nginx, когда api
лежит. Сообщения должны оставаться свободными для правки, а логика клиента — стабильной.

## Решение

- Любой не-2xx ответ: `{"error": {"code", "message", "details": [], "request_id"}}`. Формат
  описан моделью `ErrorResponse` в OpenAPI.
- Исключения не знают об HTTP. Соответствие «класс исключения → (статус, code)» задано
  в одном месте — `ERROR_SPECS` в [errors.py](../../src/app/presentation/http/errors.py).
  Выбирается самый специфичный класс по MRO.
- Неотображённая ошибка application означает баг и превращается в 500, а не в угаданный
  статус. Тест `test_every_concrete_error_has_its_own_code` обходит все подклассы
  `DomainError`/`ApplicationError` и требует для каждого запись в `ERROR_SPECS`.
- `InvalidPasswordHashError` (повреждённые данные в БД) намеренно отдаётся как 500, хотя
  это `DomainError`: клиент тут ни при чём.
- 500 не раскрывает деталей: `internal_error` и `request_id`, traceback пишется в лог.
- nginx отвечает на 502/503/504 тем же форматом (`service_unavailable`, `Retry-After: 5`).
- Версия в пути: `/api/v1`. Служебные `/health/*` и `/metrics` не версионируются.
  Несовместимые изменения выходят в `/api/v2`.

## Альтернативы

- **RFC 7807 (problem+json).** Стандартно, но поле `type` (URI) для внутреннего API избыточно,
  а единообразие с ответами nginx пришлось бы поддерживать отдельно.
- **Формат FastAPI по умолчанию** (`{"detail": ...}`). Разные формы у 422 и остальных
  ошибок, нет стабильного кода.
- **Версия в заголовке.** Чище с точки зрения REST, но хуже видна в логах и прокси.

## Последствия

- Клиент ветвится по `code`. Новое исключение без записи в `ERROR_SPECS` не пройдёт CI.
- `request_id` из тела ошибки сразу ведёт к строкам лога api и nginx.
