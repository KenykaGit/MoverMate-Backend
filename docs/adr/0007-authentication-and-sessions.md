# ADR 0007. Аутентификация: argon2id, короткий JWT, ротируемые refresh-токены

**Статус:** принято; пересмотрено 2026-10-12: семейства токенов вместо отзыва всех сессий,
перехэширование паролей при входе

## Контекст

Нужна stateless-проверка большинства запросов, мгновенный отзыв доступа (удаление
аккаунта, смена пароля, кража токена) и стойкость к утечке базы и перебору паролей.

## Решение

- **Пароли:** argon2id (argon2-cffi, профиль RFC 9106 low-memory) в worker-потоке
  (`asyncio.to_thread`). `dummy_verify` для неизвестного логина тратит столько же времени,
  сколько настоящая проверка: по времени ответа нельзя узнать, существует ли логин. Политика
  (`RawPassword`, 8–128 символов) применяется при установке пароля, а не при проверке.
- **Перехэширование при входе.** Параметры argon2 задаются настройками
  (`AUTH__ARGON2_*`). После их повышения старые хэши продолжают проверяться, а
  `CredentialsVerifier` при успешном входе видит `needs_rehash()` и сохраняет новый хэш в той
  же транзакции, что и сессию (событие `password_rehashed`). Вход — единственный момент,
  когда известен открытый пароль. `rehash()` принимает `str`, а не `RawPassword`: пароль,
  заданный по старой политике, тоже обновляется и не блокирует владельца.
- **Access-токен:** JWT HS256 на 15 минут с claims `sub`, `type=access`, `iss`, `iat`, `exp`.
  Алгоритм фиксирован при декодировании (никакого `none`), `type` не даёт выдать другой JWT
  за access-токен.
- **Пользователь проверяется на каждом запросе.** `AuthenticateUser` читает пользователя из
  БД. Удалённый пользователь получает 401 сразу, хотя его JWT ещё действует.
- **Refresh-токен** — `secrets.token_urlsafe(32)`, непрозрачная строка. В БД хранится только
  SHA-256: случайный 256-битный токен не перебирается, а детерминированный хэш позволяет
  искать по нему. Утечка БД не даёт рабочих токенов.
- **Семейства токенов.** Вход открывает сессию — новую семью (`family_id`, UUIDv7).
  Каждая ротация выдаёт следующий токен в той же семье.
- **Ротация с обнаружением повторного использования.** `RefreshTokens` отзывает
  предъявленный токен атомарно:
  `UPDATE … SET revoked_at = :now WHERE id = :id AND revoked_at IS NULL RETURNING id`.
  Если строка не вернулась, токен уже использован (кража или гонка двух запросов):
  `revoke_family` завершает эту сессию, и вору, и владельцу нужно войти заново. Другие
  сессии пользователя продолжают работать. Пишется WARNING `refresh_token_reused` с
  `family_id`.
- **Logout** завершает семью предъявленного токена, даже уже ротированного: клиент мог
  потерять ответ на refresh и держать устаревший токен.
- Смена пароля и мягкое удаление вызывают `revoke_all_for_user`: здесь скомпрометирован
  или закрыт аккаунт целиком.
- Ошибки входа неразличимы (`invalid_credentials`), лог `login_failed` содержит только
  `reason`, без логина. Логин принимает email или username: в username нельзя использовать
  `@`, поэтому неоднозначности нет.

## Альтернативы

- **Только JWT без БД.** Быстрее, но отозвать доступ до истечения токена невозможно.
- **Серверные сессии на каждый запрос.** Проще отзыв, но запрос сессии добавляется к каждому
  обращению; здесь хватает чтения пользователя по первичному ключу.
- **Отзыв всех сессий при повторе** (так было до пересмотра). Проще, но одна утечка или
  один глючный клиент разлогинивает пользователя на всех устройствах. Семья ограничивает
  ущерб сессией, в которой произошла утечка.
- **Перехэширование фоновой задачей.** Невозможно: открытый пароль известен только при входе.
- **bcrypt.** Проверен временем, но не memory-hard и обрезает пароль до 72 байт.

## Последствия

- Каждый аутентифицированный запрос делает один SELECT по первичному ключу `users`.
- Повтор refresh после сетевой ошибки клиента выглядит как кража и завершает эту сессию
  (другие устройства не затронуты). Клиенты должны сохранять новую пару до повторной
  отправки запроса.
- Индекс `ix_refresh_tokens_family_id` делает отзыв семьи одним UPDATE по индексу.
- Пароли пользователей, которые давно не входили, остаются со старыми параметрами argon2,
  пока те не войдут.
- Секрет подписи задаётся `AUTH__SECRET_KEY` (не короче 32 символов). В prod значение по
  умолчанию запрещено валидатором настроек.
