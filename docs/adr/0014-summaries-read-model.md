# ADR 0014. Сводки экранов: отдельная read model, агрегаты в SQL

**Статус:** принято (2026-10-17)

## Контекст

Фронтенд просит четыре сводки для экранов «Обзор», «Прогресс» и «Этикетки» (раздел 10
[api-endpoints.md](../../api-endpoints.md)). Требования:

- списки коробок и вещей отдаются постранично, поэтому клиент не может сам посчитать
  сводки ([frontend-backend-alignment.md](../../frontend-backend-alignment.md), 2.4);
- этикетки печатаются одним запросом, без N+1;
- признак «комната погружена» вычисляется (db-design 5.4), ручных чекбоксов нет;
- на экране не должно быть противоречивых чисел: например, «нечего паковать», когда вещь
  ещё лежит в комнате.

## Решение

- **Отдельная фича `summaries` со своей read model `AbstractSummaryReadModel`**, по образцу
  инвентаря ([ADR 0013](0013-inventory-read-model.md)): порт лежит в фиче и возвращает её
  DTO. Сводки читают несколько агрегатов (коробки, вещи, задачи) и ничего не меняют, поэтому
  в `inventory` им не место: та отвечает за изменения инвентаря.
- **`summaries` зависит от `inventory`**: берёт оттуда проверку участия
  (`project_of_member`, чужой проект — тот же 404 `project_not_found`) и DTO ссылок
  `RoomRefDTO`/`BoxRefDTO`. В ответах те же схемы `RoomRef`/`BoxRef`, что у инвентаря: у
  клиента одна модель на одну сущность. Зависимость объявлена в `APPLICATION_FEATURE_DEPS` и
  `.importlinter`.
- **Агрегаты считает SQL, по одному выражению на ответ.** Одно выражение видит один снимок:
  - `summary`: счётчики коробок, вещей и задач — один `UNION ALL` из трёх `GROUP BY`;
  - `loading-checklist`: один запрос `rooms LEFT JOIN items LEFT JOIN boxes`, группировка по
    паре (комната, коробка). «Нечего паковать» и «все коробки погружены» описывают один
    момент: вещь, которую вынули из коробки между двумя запросами, не потеряется;
  - `unpacking-progress`: один `LEFT JOIN` с `count(*) FILTER`;
  - `labels`: один запрос с `array_agg(name ORDER BY priority, lower(name), id)`.
- **Правило «комната погружена» живёт в домене**: `is_source_room_loaded` и
  `BoxStatus.has_been_loaded` (`LOADED` и дальше). SQL отдаёт факты, DTO применяет правило.
  Комната без вещей считается погруженной: из неё ничего не осталось.
- **Счётчики по статусам — объекты с полем на каждое значение enum** (`BoxStatusCounts`,
  `ItemStateCounts`, `TaskPhaseCounts`), нули включены. Сгенерированный клиент получает
  точный тип `{PACKING: number, …}`, а не `Record<string, number>`. Тест сверяет поля с enum.
- **`labels?box_ids=` — до 100 id.** Чужие, удалённые и неизвестные id пропускаются, а не
  роняют весь лист: коробку могли удалить, пока пользователь выбирал. Предел следует из
  длины строки запроса (8 КиБ у nginx): 100 UUID в неё помещаются.

## Альтернативы

- **Сводки на клиенте из полных списков.** Пришлось бы отказаться от пагинации: много
  трафика и N+1 для этикеток.
- **Сводки в Python поверх репозиториев.** Это загрузка всех коробок и вещей проекта на
  каждый показ обзора.
- **Методы сводок в read model инвентаря.** Не нужна новая фича, но `inventory` начала бы
  отвечать ещё и за задачи (`next_task`).
- **Изоляция `REPEATABLE READ` на запросы сводок.** Дала бы один снимок на несколько
  выражений. Но уровень изоляции задаётся до начала транзакции, а её уже открыла проверка
  участия. Одно выражение на ответ проще и даёт тот же результат.
- **`dict[BoxStatus, int]` в схеме.** Короче, но тип в SDK теряет ключи.

## Последствия

- `next_task` отдаёт полный `Task`. Схема `Task` и `TaskDTO` переиспользуются, когда
  появится API задач.
- Пока эндпоинтов задач нет, на стенде задачи в сводке нулевые. Модель чтения проверена
  интеграционными тестами на строках, которые пишут доменные сущности через мапперы.

## Пересмотр (2026-10-17): API задач

С появлением фичи `tasks` ([ADR 0016](0016-tasks-and-templates.md)):

- `TaskDTO` переехал в `application/tasks/dto.py`, а `next_task` читается той же функцией
  `load_task_views`, что и список задач. Поэтому `summaries` зависит ещё и от `tasks`
  (`APPLICATION_FEATURE_DEPS`, `.importlinter`).
- Проверка участия (`project_of_member`) вынесена из `inventory` в
  `application/common/membership.py`: ей пользуются все фичи проекта. Зависимость
  `summaries → inventory` осталась только ради `RoomRefDTO`/`BoxRefDTO`.
