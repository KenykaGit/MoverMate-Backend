# ADR 0005. Миграции: последовательные номера, двусторонняя проверка, инварианты в БД

**Статус:** принято

## Контекст

Схема меняется вместе с кодом, и ошибки миграций обнаруживаются только на проде: две
ветки с параллельными миграциями, модель изменена без миграции, `downgrade()` никогда не
запускался. Бизнес-инварианты, проверенные только в Python, обходятся ручным SQL или багом.

## Решение

- **Alembic с асинхронным `env.py`.** URL берётся из `MigrationSettings` (без секретов
  приложения), тесты передают его явно через `config.attributes`.
- **Последовательные id ревизий** (`0001`, `0002`…) вместо случайных хэшей: файлы читаются
  в порядке применения. `make revision` подставляет номер. Конфликт номеров после слияния
  ловят проверка single head (CI) и тест `test_revisions_are_numbered_sequentially`.
- **Двусторонняя проверка** в CI и `make migrations-check`: single head → `upgrade head` →
  `alembic check` → `downgrade base` → `upgrade head`. Интеграционные тесты применяют
  настоящие миграции (не `create_all`), сравнивают схему с моделями, предикаты частичных
  индексов и прогоняют roundtrip на отдельной базе.
- **Инварианты продублированы в БД:**
  - перечисления (статусы и т. п.) — VARCHAR + CHECK, а не нативный ENUM: новое значение
    добавляется заменой constraint в транзакции, без `ALTER TYPE ... ADD VALUE`;
  - правило, которое не выражается CHECK (например, допустимые переходы статусов),
    проверяется триггером. Он поднимает ошибку с `ERRCODE = 'check_violation'` и
    `CONSTRAINT = 'ck_<таблица>_<правило>'`, поэтому распознаётся так же, как обычный CHECK.
    Интеграционный тест сверяет триггер с доменом;
  - CHECK на нижний регистр email/username и длину хэша refresh-токена;
  - частичные уникальные индексы для soft delete ([ADR 0008](0008-soft-delete-and-savepoints.md)).
- Миграции не импортируют код приложения: значения домена переписываются литералами,
  история не меняется задним числом.

## Альтернативы

- **Случайные id Alembic.** Нет конфликтов имён, но порядок применения не виден из файлов.
- **Только проверки в домене.** Проще, но ручной `UPDATE` или ошибка в новом коде ломают
  данные молча.
- **Нативный ENUM.** Компактнее, но `ADD VALUE` нельзя откатить и до PG 12 нельзя было
  выполнить в транзакции.

## Последствия

- Изменение правила, продублированного в БД, требует правки домена и новой миграции.
  Иначе упадёт тест согласованности.
- Код каждого релиза должен работать и на предыдущей схеме (expand/contract,
  [release.md](../release.md#правила-миграций)).
