# MoverMate: сверка фронтенда и бэкенда

Источники: [MoverMate.md](MoverMate.md) (ТЗ), [db-design.md](db-design.md), [ADR 0009](0009-moving-domain-aggregates.md) и текущий фронтенд.
Сейчас фронтенд работает целиком на `localStorage` ([store.tsx](src/components/movermate/store.tsx)), а сгенерированный SDK собран по заглушке (`/users`).

Принцип разделения: инварианты, переходы и всё, что считается по большим объёмам данных, остаются на бэкенде, и фронтенд подстраивается под его модель. Бэкенд меняется там, где он расходится с ТЗ или где без него нельзя сделать нормальный UX.

## 2. Что поправить на бэкенде

### 2.1. Вернуть этап задачи

В ТЗ у задачи есть `schedule: BEFORE | DURING | AFTER`. На этом поле построен экран плана: три колонки со счётчиками ([plan-view.tsx](src/components/movermate/pages/plan-view.tsx)). Бэкенд этапы убрал, и задачи различаются только сроком `due_at`.

Выводить этап из `due_at` на фронтенде ненадёжно. Задачи без срока (а это все задачи из шаблонов, у которых срок не задаётся) не попадут ни в один этап. К тому же «день переезда» и «после» по одной дате не различить, если задача без времени.

**Решено вернуть:** колонка `phase varchar + CHECK (BEFORE, DURING, AFTER)`, обязательная, по умолчанию `BEFORE`. Этап хранится и в шаблонах. Сортировка внутри этапа остаётся `due_at NULLS LAST, id`. В «Осознанных отличиях от ТЗ» строку про этапы убрать.

### 2.2. Выбор шаблонов задач

ТЗ: «Список шаблонов, которые пользователь может добавить в свой проект». Бэкенд же копирует все шаблоны при создании проекта и не даёт эндпоинта, а на фронтенде есть кнопка «Добавить шаблон задач».

**Решено: только ручной выбор.**
- `GET /task-templates` возвращает шаблоны из файла со стабильным `id` и `phase`.
- `POST /projects/{id}/tasks/from-templates {template_ids}` копирует выбранные шаблоны в задачи.
- Автоматическое копирование при создании проекта убрать (решение 10 в db-design.md).

Связь задачи с шаблоном по-прежнему не хранится, дубли допустимы. Предупреждение о дубле, если оно понадобится, показывает фронтенд.

### 2.3. Поля коробки `title` и `is_fragile`

На фронтенде у коробки есть «Краткое описание» («Посуда на первое время») и флаг «Хрупкое». В ТЗ их нет, но:
- без описания в списке на сотню коробок видны только номер и комната, и найти коробку взглядом нельзя;
- «хрупкое» печатается на этикетке, а ТЗ упоминает его в памятках.

**Решено добавить оба:** `title varchar(200) NULL` и `is_fragile bool NOT NULL DEFAULT false`. Это две колонки без инвариантов, оба поля редактируются через `PATCH /boxes/{id}` и попадают в ответ `/labels`.

### 2.4. Эндпоинты для чтения, которые не собрать на клиенте

Данные отдаются постранично, поэтому фронтенд не сможет посчитать сводки по всем коробкам и вещам.

| Эндпоинт | Для экрана | Содержимое |
|----------|------------|------------|
| `GET /projects/{id}/summary` | Обзор, Прогресс | число коробок по статусам; задачи выполненные/всего; вещи всего / `TAKEN_OUT` / `LOST`; ближайшая невыполненная задача |
| `GET /projects/{id}/loading-checklist` | Прогресс | комнаты `SOURCE`, их коробки со статусами, признак «погружено» (5.4) |
| `GET /projects/{id}/unpacking-progress` | Прогресс | комнаты `DESTINATION`: `UNPACKED` / всего |
| `GET /projects/{id}/labels?box_ids=` | Этикетки | номер, комната назначения, `qr_token`, `title`, `is_fragile`, названия вещей; одним запросом, без N+1 |
| `GET /items/{id}/suggestions` | Потеряшки | запрос из 5.3 |

### 2.5. Пакетное создание вещей

На фронтенде вещи вводятся через запятую при создании коробки. Нужен `POST /projects/{id}/items/batch` с общими `source_room_id`, `box_id` и `priority` и списком названий (`quantity` — по желанию). Если передан `box_id`, вещи создаются сразу в `IN_BOX`.

Ещё удобнее, если `POST /projects/{id}/boxes` принимает необязательный список вещей и создаёт всё одной транзакцией.

### 2.6. Комнаты при создании проекта

Без комнат нельзя создать ни коробку (нужна `DESTINATION`), ни вещь (нужна `SOURCE`). Чтобы онбординг не требовал десятка запросов, `POST /projects` должен принимать `rooms: {source: [...], destination: [...]}` и создавать комнаты в той же транзакции. Пресеты («Кухня», «Спальня»…) предлагает фронтенд.

### 2.7. Напоминание о дате переезда

ТЗ: «Присылать уведомления при приближении дат, указанных в заданиях/проектах». В `Notification` есть только `TASK_ASSIGNED`, `TASK_REMINDER` и `BOX_CONTENTS_REMINDER`.

**Решено делать.** Предложение:
- Новый тип `MOVING_DATE_REMINDER`: адресаты — все участники проекта, условие отправки — проект активен.
- Смещения хранятся у проекта по аналогии с `TaskReminder`: `ProjectReminder (project_id, offset_days)` внутри агрегата `Project`.
- `moving_date` — дата без времени, поэтому нужна точка отсчёта. Варианты: начало дня (например, 09:00) в часовом поясе проекта, тогда нужна колонка `Project.time_zone`, которую клиент передаёт при создании, или фиксированное время в UTC. Выбор за бэкендом.
- При изменении `moving_date` ожидающие напоминания пересчитываются, при удалении проекта или участника отменяются (так же, как в 10.2).

### 2.8. Ответ по QR-токену

`GET /b/{qr_token}` должен возвращать не только коробку, но и уровень доступа (`READ` | `WRITE`) и минимум данных о проекте (название). Тогда фронтенд сам решит, какую карточку показать. Без входа в режиме `PROTECTED` ответ 401, чтобы фронтенд перенаправил на вход и вернул пользователя на ту же ссылку. Сейчас в 8-м разделе этот случай описан как «перенаправление на вход», но редирект — задача клиента.

### 2.9. Контракт API (договориться до перегенерации SDK)

- **OpenAPI.** Опубликовать спецификацию, фронтенд генерирует SDK (`npm run openapi`).
- **Enum.** Строки в верхнем регистре во всех DTO, включая приоритет (`FIRST_NECESSITY`…), хотя в БД он `smallint`.
- **Ошибки.** Единый формат с машинным кодом, например `{"code": "BOX_STATUS_TRANSITION", "detail": ...}`. Фронтенду нужно различать 409 «переход вне матрицы», «имя занято», «комната используется», «владелец проектов» и показывать понятный текст.
- **Идемпотентные ответы.** При повторе того же статуса возвращать 200 с актуальным состоянием (не 204 и не 409), чтобы клиенту было просто откатывать оптимистичное обновление.
- **Токены.** Как отдаются access и refresh. Предложение: refresh в `httpOnly`-cookie, access в теле ответа. Тогда `middleware.ts` сможет перенаправлять на `/login` до рендера, а refresh не будет доступен из JS.
- **Удаление проекта — только владелец.** Остальным участникам `DELETE /projects/{id}` отвечает 403. В DTO проекта нужен `owner_id` (или `is_owner`), чтобы фронтенд скрывал кнопку.
- **Пагинация.** Формат курсора (`after`), размер страницы, наличие следующей страницы.

## 3. Что поправить на фронтенде

### 3.1. Перейти на API

- Заменить `MoverMateProvider` с `localStorage` на запросы через сгенерированный SDK. Удалить `uid()`, `createDemoProject()`, `normalizeProject()` и тесты к ним: идентификаторы и данные выдаёт сервер.
- Списки коробок, вещей и журнала грузить постранично, счётчики брать из `summary` (2.4).
- Мутации статусов и состояний делать оптимистично, с откатом при 409.

### 3.2. Коробка

- Показывать `number` («№ 12») вместо `BOX-101`, `id` использовать только в URL и запросах.
- Новая коробка всегда в `PACKING`. Убрать автоматический `packed` при наличии вещей ([store.tsx:166](src/components/movermate/store.tsx#L166)).
- Статус менять через `PUT /boxes/{id}/status`. Кнопки ±1 шаг уже совпадают с матрицей.
- «Заполнить позже»: вместо чекбокса сделать «Напомнить заполнить» с пресетами времени («через час», «вечером», «завтра»), показывать запланированное напоминание и возможность его отменить. Учесть, что напоминание приходит только создателю коробки и отменяется при переходе в `PACKED`.
- Удаление: в подтверждении указывать, что удалятся и N вещей в коробке.
- `title` и «Хрупкое» оставить (п. 2.3), «Хрупкое» печатать на этикетке.

### 3.3. QR-коды и этикетки

- В QR кодировать `${origin}/b/${qr_token}`. Убрать `salt` и `?key=` ([labels-view.tsx:7](src/components/movermate/pages/labels-view.tsx#L7)).
- Сейчас логика перевёрнута относительно ТЗ: ключ добавляется только в `protected`, а в `open` ссылка открывается по одному `id`. На бэкенде токен есть всегда, а режим проверяется в момент запроса.
- Добавить маршрут `src/app/b/[token]/page.tsx`. Показывать полную карточку при доступе `WRITE`, карточку только для чтения при `READ`, при 401 — вход с возвратом на ту же ссылку. Старый `/box` удалить.
- Поправить подписи режима в настройках: `PROTECTED` — «только участники проекта», `OPEN` — «любой со ссылкой может посмотреть, менять могут только участники».
- Печать: выбор нескольких коробок и данные из `/labels` (2.4).

### 3.4. Комнаты

- Убрать захардкоженные 4 комнаты ([movermate.const.ts:59](src/configs/consts/movermate.const.ts#L59)). Сделать экран или раздел настроек с двумя списками: «Откуда» и «Куда».
- В мастере создания проекта предлагать пресеты для обоих списков (2.6).
- Иконку подбирать по ключевому слову в названии, иначе показывать нейтральную.
- Удаление комнаты, на которую ссылаются коробки или вещи, возвращает 409: показывать понятное объяснение.

### 3.5. Вещи

Это самое крупное изменение модели. Вещь больше не вложена в коробку:

| Сейчас | Нужно |
|--------|-------|
| `unpacked`, `lost` | `state: TO_PACK \| IN_BOX \| TAKEN_OUT \| LOST` |
| только название | + `source_room_id` (обязательно), `quantity`, `priority` |
| вещь существует только в коробке | вещь может быть вне коробки |

- **Список для упаковки** (новый экран или вкладка): вещи `TO_PACK` с сортировкой `priority, name, id`, действие «положить в коробку».
- **Добавление в коробку:** в форме нужен выбор комнаты «откуда». Подставлять последнюю использованную комнату, так как коробку обычно собирают в одной комнате.
- **«Распаковано»** означает `TAKEN_OUT`. Вещь уходит из коробки (`box_id = NULL`), поэтому счётчик «Распаковано 1/3» на карточке коробки заменить на «в коробке N вещей». Прогресс распаковки считать по коробкам `UNPACKED`.
- **Распаковку** разрешить при любом статусе коробки. Сейчас она заблокирована до `delivered` ([box-details.tsx:160](src/components/movermate/box-details.tsx#L160)).
- **«Нашлась»:** спросить, где нашлась вещь. Варианты: «в исходной комнате» (`TO_PACK`), «в коробке…» (`IN_BOX`, с подсказками из `/suggestions` первыми) и «уже на месте» (`TAKEN_OUT`).

### 3.6. Задачи

- `due` как текст заменить на `due_at`: дата и необязательное время, отображение в часовом поясе пользователя.
- `assignee` как текст заменить на мультивыбор из участников проекта.
- Добавить напоминания: пресеты «за 2 часа», «за день», «за неделю», произвольное значение в часах. Поле доступно только при заданном сроке. При очистке срока предупреждать, что напоминания удалятся.
- Добавить поле `description`.
- Отметку выполнения делать через `complete` / `reopen`.
- Три колонки этапов оставить (п. 2.1), значения `stage` привести к `phase`: `BEFORE | DURING | AFTER`.
- «Добавить шаблон задач»: модалка со списком шаблонов из `GET /task-templates`, сгруппированных по этапам, с чекбоксами. Выбранные отправляются одним запросом. Дедупликацию по названию убрать, вместо неё помечать шаблоны, совпадающие с существующими задачами.

### 3.7. Участники проекта

Новый раздел в настройках проекта: список участников, добавление по `username`, удаление. Владелец помечен и не удаляется. Без этого раздела нельзя назначать ответственных.

Кнопку «Удалить проект» показывать только владельцу (`canDelete` в [forms.tsx](src/components/movermate/forms.tsx) считать по `owner_id`).

### 3.8. Прогресс и обзор

- **Погрузка по комнатам** строится по комнатам «откуда» из `loading-checklist`. Ручные чекбоксы `roomsLoaded` убрать: признак вычисляется.
- **Первый день** — это вещи с `priority = FIRST_NECESSITY`, а не захардкоженный список `firstDay`. Пункт выполнен при `TAKEN_OUT`. Переход `TO_PACK → TAKEN_OUT` запрещён матрицей, поэтому неупакованную вещь показывать как «не упакована — возьмите с собой», без чекбокса.
- **Потеряшки** — это `items?state=LOST` с подсказками. Текст «числится в BOX-101» убрать: у потерянной вещи нет коробки.
- **Обзор**: все цифры брать из `summary`.

### 3.9. Поиск

- Фильтрацию на клиенте ([boxes-page-client.tsx:49](src/components/movermate/pages/boxes-page-client.tsx#L49)) заменить серверным `items/search` с debounce. Результат — вещи с местом: номер и статус коробки или состояние и комната «откуда».
- Если запрос — число, дополнительно искать коробку по номеру.
- Учитывать, что поиск идёт по началу слова: «зар» найдёт «зарядка», а «ряд» — нет. Подсказку в placeholder сформулировать соответственно.
- Фильтр коробок по комнате передавать в запрос как `destination_room_id`.

### 3.10. Аккаунт

- Подключить реальные регистрацию и вход, перенаправление через `middleware.ts`, обновление токена.
- `username`: от 3 до 32 символов, приводить к нижнему регистру при вводе или показывать, что регистр не важен.
- Удаление аккаунта: при 409 объяснять, что сначала нужно удалить свои проекты.

### 3.11. Web Push (отложено)

- Service worker, `manifest.webmanifest` (на iOS PWA обязательна для push), HTTPS на стенде.
- Переключатель «Уведомления» в профиле: получить VAPID-ключ, подписаться, отправить подписку. Работать без подписки должно всё остальное.

Пока push нет, у пользователей не будет подписок, и бэкенд пометит все уведомления как `SKIPPED`. Поэтому UI настройки напоминаний (напоминание о содержимом коробки в 3.2, напоминания задачи в 3.6, напоминания о дате переезда) делать вместе с push. Бэкенд при этом реализует очередь уведомлений сразу. «Отложенное заполнение» из ТЗ до появления push закрывается списком коробок в статусе «Собирается» без вещей.

### 3.12. Памятки

Бэкенд хранит памятки файлами и не даёт для них API. Предлагаю держать их на фронтенде статикой в `src/configs/consts/` и показывать на экране плана и в карточке хрупкой коробки.

## 4. Принятые решения (2026-10-17)

1. Этапы задач возвращаются (2.1, 3.6).
2. Шаблоны задач добавляются только ручным выбором, автоматического копирования нет (2.2, 3.6).
3. У коробки есть `title` и `is_fragile` (2.3, 3.2).
4. Напоминание о дате переезда делаем (2.7).
5. Удалить проект может только владелец (2.9, 3.7).
6. Журнал событий в UI пока не нужен. Бэкенд его ведёт, эндпоинт чтения можно не делать.
7. Web Push на фронтенде откладывается вместе с UI напоминаний (3.11).
